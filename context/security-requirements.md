# Security requirements

Two real users only (real account "Sam" + seeded demo account) — no public signup, no arbitrary strangers connecting real bank accounts. That scope decision keeps the trust/liability surface small; do not add open registration without a deliberate, separate decision.

- Password hashing + proper auth — already in place (`werkzeug.security.check_password_hash`), must carry over into whatever the new token-based auth scheme is.
- CSRF protection on state-changing requests — was form-based (`flask_wtf.CSRFProtect`); needs a token-API-appropriate equivalent once the frontend moves to a separate-origin React SPA (CSRF tokens don't apply the same way to a JSON API using bearer tokens — don't drop the protection, translate it).
- **Known gap, fixed by the auth rework (see `changes/001-api-spa-rewrite/`)**: Flask's old session cookie was signed, stateless, client-side, with no server-side record — "logout" only stopped the legitimate client from resending it, a copied/replayed cookie still worked. Fixed by moving to a short-lived access token (~15 min, held in memory only, never persisted) plus a refresh token stored server-side in a revocable table. "Session" is retired as a term for this project going forward — use "access token" / "refresh token."
- **Token storage (decided during grill of `changes/001-api-spa-rewrite/plan.md`)**: access token lives in memory only (lost on page refresh, silently re-minted via `/api/refresh` — this is fine). Refresh token lives in an httpOnly, Secure, SameSite=Strict cookie — invisible to JS, so an XSS bug can't steal it. Only `/api/refresh` touches that cookie and needs its own lightweight CSRF protection (double-submit token or origin check); the rest of the API stays bearer-token-only with no CSRF needed.
- Encryption at rest for the stored SimpleFIN Access URL (SimpleFIN's own stated requirement) — `simplefin-integration.md` has details. Also needs secrets management for the encryption key itself, and any deploy-time credentials (ties to EKS IAM/secrets patterns).
- Per-user data isolation, including IDOR checks — `get_owned_category()` in the existing `app.py` is the established pattern (check ownership by direct column comparison, not by trusting a joined relationship). Carry this pattern into the new API layer for every resource, not just categories.
- Demo-user data isolation must be verified explicitly, not just assumed from separate user IDs — given the demo account is shown publicly, a leak there is the one failure mode this whole two-user design exists to prevent.
- HTTPS everywhere in production; ties to whichever AWS/EKS ingress setup gets built.
- An OWASP Top 10 pass is expected before the app is ever live with Sam's real bank data — treat this as a real gate before a production deploy, not a nice-to-have.
